# AgentOS settings in `vitul.conf.json`

Vitul stores desktop, mobile, and AgentOS project settings in one root
`vitul.conf.json`. Use `vitul agentos init` to create the file in an existing
project, or edit the `agentos` section generated by `vitul create`.

## Map the requirement to configuration and implementation

This page owns AgentOS root fields and their constraints. Check cross-platform
[Support](../../../../docs/SUPPORT.md) and [Architecture](../../../../ARCHITECTURE.md)
first. Choose app type and execution mode before configuring an individual feature.

| Requirement/decision | Root entry point | Complete together | Verify |
| --- | --- | --- | --- |
| Hosted website | `agentos.type: "remote-web"`, `agentos.web.url` | HTTPS website; no local process, build steps, or source artifacts | `any` package opens the intended website in Shell |
| Local service | `agentos.type: "process"`, `build`, `run` | Compile, collect, start, listen, health check, frontend entry | Packaged service/page reach readiness and serve business calls |
| Container or host execution | `agentos.execution` | Default container; native needs a full profile and persistence; decide by host access/isolation | Correct inspected mode and matching host prerequisites |
| Persistent data | `agentos.data.persistent` | Code actually uses host-provided `DATA_DIR`; place config, databases, and caches deliberately | Expected data survives restart |
| Window layout | `agentos.open` | Mode, title bar, dimensions; host reports actual applied layout | Correct multi-window, resize, and title-bar interaction |
| Last-window-close behavior | Native `lastWindowClose`; host protocol for other modes | Backend tasks, host entry points, stop policy, child cleanup; separate from autostart | Expected close, reopen, exit behavior |
| System APIs | `agentos.permissions`, host calls | Declare and invoke capability; handle denial and unavailability | Expected behavior with approval, denial, and missing host support |
| External programs | Root `bundle.externalBin` or `agentos.build.artifacts` | Host sidecars require `native.sidecars`; correct binaries, calls, and cleanup | Correct installed binary actually starts and stops |
| Providers/deployment | `agentos.providers`, `deployment`, permissions | Protocol methods, runtime integration/implementation, host authorization/services; built-ins need no packaged executable | Valid declaration plus real calls, failure handling, cleanup |
| Proxy/TUN | `agentos.network`, native profile, permissions | Executables, snapshots, host networking, restoration; see below | Package digests plus actual network effects and stop recovery |
| OpenTool | `agentos.rpc`, backend routes | Paths, discovery, method implementation, frontend calls | Actual calls in the installed app |

Language, themes, and business UI require code too. See the
[WebApp integration guide](../../../../examples/agentos/process/docs/webapp-localization-theme.md).
These entry points locate settings; no table row is a complete configuration.

## Configuration layers and paths

Root `schemaVersion: 2`, package `manifestVersion: 1`, and OpenTool `rpc.version: 2`
are independent formats. Edit root `vitul.conf.json`; do not paste an internal
projection or an example's `app.json` into it. Fields below are under root
`agentos` unless explicitly identified as root fields.

| Group | Related constraints |
| --- | --- |
| `targets`, `buildImage` | Declare ARM64/x64 targets; artifacts and runtime dependencies must match. A build image does not make arbitrary binaries cross-architecture |
| `build.steps` | Generate artifacts in the project; include command, arguments, working directory, environment. A declared step does not prove every file was generated |
| `build.artifacts` | `from` is project-relative; `to` is package-relative; `targets` can select architecture-specific artifacts |
| `run.command`, `args` | Use package layout. Path commands must be covered by artifacts; scripts/resources named in arguments must be packaged too. Supply required interpreters/libraries in the target environment |
| `run.port`, `healthCheck`, `readyTimeout` | Match the listener and a real health route; reach readiness within the timeout; `frontendEntry` must resolve |
| `run.env` | Match the backend's actual configuration; native profiles reject reserved host variables |
| `permissions`, `providers`, `deployment`, `network` | Declaration, authorization, implementation, and host services are separate dependencies; details follow |
| `data.persistent`, `execution` | Persistence and process lifecycle are separate; persistence does not keep a process running after window closure |

Use `agentos.run.port` (default `9627`). Deprecated `agentos.port` is used only when
`run.port` is absent and emits a migration warning; conflicting values fail.
Update `run.env.PORT` too if the backend uses it. The CLI cannot infer the listener
configuration from application code.

## Minimal process structure

The example illustrates field placement. Supply `dist/`, `service/server.js`, and
the `/health` route, and ensure Node.js exists in the target runtime. This is not
a runnable project with service source included.

Process apps declare their build and launch configuration under `agentos`:

```json
{
  "schemaVersion": 2,
  "productName": "Example",
  "identifier": "com.example.app",
  "version": "1.0.0",
  "agentos": {
    "type": "process",
    "targets": ["agentos/arm64", "agentos/x64"],
    "execution": { "mode": "container" },
    "build": {
      "steps": [],
      "artifacts": [
        { "from": "dist", "to": "web" },
        { "from": "service", "to": "service" }
      ]
    },
    "run": {
      "command": "node",
      "args": ["service/server.js"],
      "port": 9627,
      "healthCheck": "/health"
    }
  }
}
```

## Execution mode and native profile

Omit `agentos.execution`, leave its `mode` empty, or set it to `container` to
use the default container runtime. Vitul supports native execution only with
the AgentOS native process profile v1: `mode: "native"` must include the
`native` object. The older `{ "mode": "native" }` form is rejected so builds
cannot silently produce the legacy execution identity, which is not visible
and manageable in the AgentOS account UI. Native profile processes run on the
Linux host as the authenticated AgentOS account and still require explicit
high-risk consent on install or update.

To configure the native profile, add the `native` object and enable persistent
data:

```json
{
  "schemaVersion": 2,
  "productName": "Generic Service",
  "identifier": "org.example.generic-service",
  "version": "1.0.0",
  "agentos": {
    "type": "process",
    "targets": ["agentos/arm64", "agentos/x64"],
    "execution": {
      "mode": "native",
      "native": {
        "version": 1,
        "identity": "desktop-user",
        "scope": "agentos-account",
        "lastWindowClose": "background",
        "stopGracePeriodMs": 20000
      }
    },
    "data": { "persistent": true },
    "build": {
      "steps": [],
      "artifacts": [
        { "from": "dist", "to": "web" },
        { "from": "service", "to": "service" }
      ]
    },
    "run": {
      "command": "node",
      "args": ["service/server.mjs"],
      "port": 9627,
      "healthCheck": "/health",
      "readyTimeout": 30,
      "autoStart": false,
      "frontendEntry": "/"
    }
  }
}
```

For profile v1, `version`, `identity`, and `scope` are required and fixed to
`1`, `desktop-user`, and `agentos-account`. `lastWindowClose` accepts `stop`
or `background` and defaults to `stop`; `stopGracePeriodMs` accepts 0 through
30000 and defaults to 5000. Vitul writes these defaults into the packaged
`app.json`. The profile requires persistent data, one backend per bundle ID
in an authenticated AgentOS account, and a manifest-v1 process App. Vitul
always emits `run.autoStart: false`; profile configs cannot enable autostart.
`background` only keeps a running
backend alive after its last window closes; it does not start the App at boot
or login.

With `lastWindowClose: "background"`, AgentOS Shell shows its generic tray
with Open and Exit actions while the backend is running. This tray does not
need an App permission or helper. The separate `native.tray` permission is for
an App's own custom tray through AgentOS's tray socket and should be requested
only when the App uses that API. Profile Apps cannot override AgentOS-owned
environment keys such as `HOME`, `PATH`, `XDG_RUNTIME_DIR`, Wayland/D-Bus
session values, `AGENTOS_TRAY_SOCKET`, `LD_PRELOAD`, or `LD_AUDIT`.

Native mode requires a process app. A desktop-user Native App may declare
AgentOS built-in Host Providers (including External Wayland and
system-deployment) and package-owned business Providers, subject to the
manifest permissions. Native system-deployment can perform authorized host
package, kernel-module, Binderfs, and fixed systemd-service actions.
`linux.device.assign`, `linux.bind-mount`, and LXC actions remain container-only;
apps that need container device mappings or mounts should keep the default
container mode.

### Native App network profiles

Vitul supports AgentOS Native App network manifest v1 for process apps using
`execution.mode: "native"` and the native profile v1 with
`identity: "desktop-user"`. Declare package-relative executable paths; Vitul
computes their lowercase SHA-256 values from each target's final staged files.
Do not provide digests in `vitul.conf.json`. TUN configuration is submitted by
the App at runtime and is not a package artifact.

The following generic proxy profile shows the configuration shape. Add the
referenced executable through `build.artifacts`, including the final package
path `bin/network-client`. A complete proxy and TUN config example is available
at [`examples/agentos/native-network/`](../../../../examples/agentos/native-network/README.md):

```json
{
  "permissions": ["native.providers", "native.network", "native.system-proxy"],
  "network": {
    "protocolVersion": 1,
    "executables": [{ "id": "network-client", "path": "bin/network-client" }],
    "proxyProfiles": [{
      "id": "account-proxy",
      "executable": "network-client",
      "http": { "host": "proxy.example.invalid", "port": 8080 },
      "https": { "host": "proxy.example.invalid", "port": 8443 },
      "socks": { "host": "127.0.0.1", "port": 1080 },
      "bypass": ["localhost", "127.0.0.0/8", "::1"]
    }]
  }
}
```

For TUN, add `native.tun` and a `tunProfiles` entry with bounded fixed
`arguments`, `configuration: { "source": "runtime-snapshot", "maxBytes": 4194304 }`,
`interfaceName`, both `ipv4` and `ipv6` set to `true`, and the fixed
`exitPolicy: "restore-previous"`. `maxBytes` must be an integer from 1024 through
4194304. The argv must contain `${config}` at least once; it cannot contain
other placeholders, host absolute paths, or path traversal segments. Only the
package executable goes in `build.artifacts`. For each `tun.start` request the
App submits its current configuration snapshot, outer endpoints, and DNS
servers. Vitul generates the built-in `org.agentos.network` Provider and its
complete v1 method set; do not declare an app-owned Provider for it.

Network declarations require `native.providers` and `native.network`.
`native.system-proxy` is required exactly when `proxyProfiles` is non-empty,
and `native.tun` exactly when `tunProfiles` is non-empty. Network profiles can
coexist with other App-owned Providers when they follow the `native.providers`
rules. `org.agentos.network` is generated by Vitul with its fixed v1 method set
and cannot be redeclared by the App. Network profiles require native process
execution; remote-web packages cannot declare them. Run `vitul agentos validate`
and `vitul agentos inspect` before packaging.

Manifest validation confirms the declaration and packaged executable digests.
It does not prove that a third-party tunnel kernel or remote tunnel endpoint is
compatible with the AgentOS sidecar. Proxy behavior and TUN availability also depend on the AgentOS
host and its network services. The current Linux TUN backend requires the
AgentOS service with systemd and systemd-resolved, `iproute2`, `nft`,
`/dev/net/tun`, and administrator-enabled IPv4 and IPv6 forwarding. It also
checks the host resolver, policy rules, DNS routing domain, and physical route
to each fixed IPv4 endpoint. The system proxy backend writes the authenticated
account's GNOME proxy settings; applications that ignore those settings may
continue to connect directly.

For a hosted site, set `agentos.type` to `remote-web` and `agentos.web.url` to
an HTTPS address. Remote-web packages open the site in AgentOS's embedded CEF
window and do not package a local process.

Run `vitul agentos validate` before building. Use `vitul agentos inspect` to
review the projected app profile and declared AgentOS targets.


## From configuration to acceptance

1. `pnpm vitul agentos validate` checks declarations and some source-file constraints;
   fix root settings or source files when it fails.
2. `pnpm vitul agentos inspect` reports effective app type, targets, mode, port,
   permissions, and persistence; it does not start the app.
3. `pnpm vitul build --target agentos` builds and collects each selected target.
   Check packaged `app.json`, entry points, files referenced by arguments, resources,
   and binaries. A packaged component is not proof that code invokes it.
4. Install in the target Shell and test the requirement's success, denial, missing
   resource, restart, and exit scenarios as applicable.

Browser or desktop development success does not prove the installed AgentOS app.
Diagnose in order: field consumed by this command, generated output, packaged
files, actual startup, host support/authorization, observable outcome. Report
verified and unverified conditions individually; config/build success does not
substitute for acceptance.
